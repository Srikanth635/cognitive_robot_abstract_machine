CONTINUATION UPDATE: TRANSPORT/CARRYING COMPOSITION
Release 0.19.0; completed 2026-11-12.

The user requested the remaining compositions/refinements, starting with
transport/carrying. This release adds the first composition module in a new
compositions/ directory. There are still seven primitive reusable domains;
transport/carrying is a composition, not an eighth primitive domain. The registry
now contains 38 ontology documents. The generic aspect assembly is unchanged.

Read compositions/TRANSPORT_CARRYING.md, tools/transport_carrying.py and
reports/release-0.19.0.json before continuing. The earlier handoff and 0.18.0
update retain their dated scope; this file describes the new increment.

Four synthetic fixtures cover destination carrying, route carrying, and each
with an optional orientation requirement. Two concrete action kinds/classes are
used. A broad TransportDescription remains an extension point; grasped carrying
does not define every transport technique. Pickup, release and placement are
separate actions. Cart, supported, pushed, dragged, multiple-grasp and handover
techniques require explicitly designed profiles rather than weakening this one.

The composition reuses cloned holding/navigation descriptions, their participant
identities, roles, parameters, capabilities and exact condition expressions.
It binds the same load, manipulator, carrier and destination consistently.
The navigation footprint must identify both carrier and load. Carrier arrival
alone is insufficient: the load must also be reported in the destination.

Success requires maintained holding, navigation success, interval load support
and envelope preservation, and load arrival. Route variants also need route
compliance. Orientation variants use interval maximum angular deviation from an
explicit quaternion target/frame, not endpoint orientation and not a full pose
fixed to the world. This first orientation profile constrains full orientation;
tilt-only upright constraints with free yaw remain extensions.

Parent, holding and mobility use distinct scoped contexts. Each supplied child
dictionary must name its expected context. Parent and both children must
explicitly bind exactly the same time window. Missing child intervals are not
copied from the parent. Unqualified interval evidence is withheld. Time metadata
only scopes evidence; it does not verify continuous sensing or accept beliefs.

Use the composition-specific assess API; do not flatten child input dictionaries
and run the parent condition through the generic evaluator. That would bypass
component context/interval policies. Each child is evaluated separately with its
existing domain inspector, then the results are combined under three-valued
conjunction/disjunction. Preconditions, success and explicit faults remain
separate; concurrent success/fault reports remain visible.

A parent-context monitor attaches to the cloned mobility execution phase and
checks current hold, borne load and loaded-envelope clearance. False/Unknown
declares suspension, but no monitor response or controller is executed. Child
phase graphs remain descriptive. This is not a concurrent execution scheduler,
resource allocator, terminating plan, physical solver or readiness certificate.

All new claims are Proposed and synthetic. There are no numerical physical
defaults, accepted observations, world bindings or generated safe thresholds.
The four records have exact statement coverage for their reachable descriptive
links. The builder only regenerates the new examples and was checked for graph
equality against its previous output. Original fixtures are preserved.
